# Notes for working on this repo

- Product owner: the PHO & CO owner. Confirm any new feature idea with them before building it.
- Sites: EAS (Eastcote, restaurant), WEM (Wembley, production, Reg 853 approved), SYD (Sydenham, closed until it reopens and left out of the pilot).
- Keep business rules in `src/lib/domain/`, pure and tested. UI and actions call them; they never re-implement them.
- Every data change goes through `Store` (`src/lib/data/store.ts`). Add the method to the interface, `demo-store.ts` and `sql-store.ts`.
- Server actions in `src/app/actions.ts` must check the session (`requireCtx` / `requireOwner`), validate input with zod and write an audit entry for anything a manager or an inspector would care about.
- Food-safety records are append-only. Correct by adding a new entry, never by editing.
- No staff personal data, PINs or secrets in the repo. Demo people are labelled "(demo)".
- Before pushing, run `npm run typecheck && npm run lint && npm test && npm run build`.
- Brand: cream `#F6F1E7`, green `#2F4A3A`, sage `#DCE3D6`, orange `#C2611A`. Fonts Barlow Condensed (headings), Be Vietnam Pro (body).
- Database: Supabase project `phoco-ops-hub` (ref iklgabptdlwjwwngepyc, eu-west-2 London). The org's other project ("Pho & Co's Project") is a separate purchase-ledger app: never touch it.
- Schema changes go in a new numbered file in `supabase/migrations/` and are applied to Supabase too.
- Rota: the app never writes to the rota sheets. Imports arrive at `/api/rota/import` (per-site token, hashed in `rota_sources`). Rules in `src/lib/domain/rota.ts`; times are London wall-clock (`src/lib/domain/time.ts`).
- Secrets the server generates (VAPID push keys, scheduler token) live in `app_secrets`; the Supabase cron job `ops-hub-reminders` reads the `cron` token from there.
- Kitchen prep: master list in `PREP_MASTER` (`src/lib/domain/prep.ts`) and `prep_items`; a test keeps them in step. Never delete or renumber an item: retire it with `active = false`. Submitted handovers and their entries are kept (database guards).
- Handover tab (`src/app/handover/`) = notes (`handover_items`) + prep handover. Note rules (which notes show, which go on a report) are in `src/lib/domain/handover.ts`. Old `/prep` links redirect there.
- Team rota (`/rota`): `buildTeamWeek` in `src/lib/domain/rota.ts`. Staff see published weeks with times only; paid hours (`shifts.paid_hours`, from the Export tab) and draft weeks are for owners and managers. Works for both session scopes (tablet and own phone).
- Roles (`person_sites.role`, per site): owner, ops (operations manager), manager, staff. `isOwner`/`isOps`/`isLead` and `leadSites` are in `src/lib/domain/access.ts`; `managedSites` includes ops. An operations manager gets the overview (`/owner`, `requireLead()` in `src/lib/session.ts`, their sites only), staff and manager accounts at their sites (`canManageAccount`, `canGiveAccess`, `givableRoles` in `staff.ts`), tablets at their sites, and the full app on their own device. Owner-only: closing/reopening sites (and lifting a closure's freeze: `canUnfreeze`, `canMarkLeft`, `canRejoin`), rota sheet connections, right to work (and accounts that can see it), owner and ops accounts. A full session off a tablet needs `runsSite` (owners anywhere, ops at their sites); `remoteSignIn` picks where a staff ID sign-in lands and `canSwitchTo` limits "Work at". Their time off is decided by an owner (`canDecide` takes the requester; `timeOffDeciders`, `seesRequest`). Their activity log: `activityFor` in `activity.ts`.
- SOP library (`/library`; `library_docs`, `library_versions`, `library_acks`, `media`; rules in `src/lib/domain/library.ts`; loaders in `src/lib/library-service.ts`). Versions go draft → in_review → published → superseded (or discarded); one published and one open version per document (unique indexes); database triggers allow only those moves, refuse changing a published version except to mark it superseded, and nothing is deleted (a document's code never changes). Every change names the revision it was shown (`rev`) and is refused if it has moved on (the page offers the latest: `stale`). Writers: `canDraft` (managers and leads); approvers: `canApprove` (owner, ops). An approver acts for every site an SOP covers (`docReach`: its published version's sites and the new version's, so narrowing it still counts; `coversReach`): approving or sending back (`canReview`, never a version you wrote, changed or sent: `contributors`; owners may), taking back or discarding someone else's version (`canWithdraw`, `canDiscard`), retiring and bringing back (`canRetire`, `canReinstate`). The store re-checks contributors when publishing; publishing, discarding and retiring lock the document row before its versions. Discarding the only draft of a never-published SOP retires it. Who reads a version: `readsAt` (staff by sections, managers by the site's sections, never owners, open sites only); acks are per version, and only the approver is counted as having read it. Lists and counts load `libraryDocs(kind, { light: true })` (sections, no steps). The editor keeps unsaved changes in sessionStorage (per tab, per person) and offers them back; `createDraft`/`saveDraft` return an error rather than redirecting when the session has ended (the editor shell is `DraftForm`, shared by every kind). Photos (JPEG only): `POST /api/media` (writers, full scope; ≤ 2 MB read with a cap, real size from `jpegSize`, `PHOTO_DAILY_LIMIT` a day each, checked again atomically in `addMedia`), `GET /api/media/<id>` (anyone signed in; cached 10 minutes, then an ETag check). The owner can erase one (`erasePhoto`, audited; it shows as removed everywhere and is dropped from a draft when it's saved, `dropPhotos`); photos no version uses (discarded drafts don't count) are cleared after `PHOTO_KEEP_UNUSED_DAYS` by `tick()` (09:00–10:00), and the database refuses deleting one in use. The `body` JSON is checked by `cleanSop` (always) and `readyForReview` (to send or publish).
- Recipe handbook (`/library/recipes`, `/library/allergens`; rules in `src/lib/domain/recipes.ts`): prep recipes (`prep`: a batch with what it makes, ingredients, method, storage, shelf life) and dish specs (`dish`: one portion's components, build steps, kitchen notes, dietary tags) are library kinds with the same drafts, approval, versions and four-eyes rules as SOPs (`isKind`, `codePrefix`: PREP-…/DISH-…). Bodies are cleaned by `cleanRecipe` and checked by `recipeReady` (every one of the 14 allergens plus E120 marked: contains / can be left out (dishes) / free). Amounts are a number and a unit (`Item.qty` optional: "a drizzle"), scaled with `scaleQty`/`formatQty`/`factorFor`/`inUnit`. Recipes are only on the full app, for writers and kitchen staff (`seesRecipes`: BOH or PROD at an open site, any kitchen's recipes); front of house and own phones get a dish's allergens (`/library/allergens/<id>`) instead. A dish component may link to a prep recipe (`Item.prep`, checked on save); `dishWarnings` flags tags or linked recipes that disagree (it doesn't block). The matrix (`allergenMatrix`, `fitFor` for "a guest avoids") is for everyone. Publishing a dish whose allergens changed (`allergenAlert`) dates it (`library_versions.allergens_changed_at`, kept by later versions); everyone at the dish's sites but owners (`alertedAt`) confirms once (`allergenAlerts`: an ack on any version of that dish after the change counts; acks carry `docId`), shown on Today and My shifts; managers see who has (`alertStats`).
- Manager tools live under `/manage` (`requireManager()` in `src/lib/session.ts`; `managedSites`/`canManage` in `src/lib/domain/access.ts`). Tiles and their counts: `src/app/manage/ManageTiles.tsx` and `counts.ts`. Owners see the same tiles on `/owner`.
- Inspection records (`/manage/records`, rules in `records.ts`) and the weekly report (`/manage/report`, `report.ts`, loaded by `src/lib/report-service.ts`, also used for the Monday message) only read existing records. A site's checklists count from its first recorded run (`trackingFrom`); only checklists with a due time are expected daily.
- Team notices (`announcements`, `announcement_reads`; rules in `notices.ts`), time off (`time_off`; `timeoff.ts`) and certificates (`staff_certificates`; `certificates.ts`). Certificates and notices are never deleted: they're ended or marked removed. Right to work is private: only people with `people.sees_right_to_work` (today, just the owner) can see or record it (`canSeeRightToWork`), and it has no document number.
- Messages to people go through `queueNotice` with a `dedupeKey` (unique across the table, so include the recipient). Kinds are listed in the `notifications_kind_check` constraint (migration 0008); add new kinds there too. Certificate reminders are worked out in `tick()` between 09:00 and 10:00 London. Quiet hours are 22:00–08:00; urgent messages (kit not working, P1 tasks) go out until midnight (`afterQuietHours(now, true)`).
- Equipment (`equipment`, `equipment_events`; rules in `equipment.ts`): faults, updates, fixes and services are separate append-only events (a database trigger refuses changes; a fault is fixed once). Anyone at the site can report (either session scope); updates and fixes need the full scope; the register and services are for managers. QR labels open `/equipment/<id>`; `safeNextPath` is the only way back after sign-in.
- Tasks (`tasks`; rules and the task centre's priorities in `tasks.ts`; gathered per site by `src/lib/task-centre.ts`). The centre only reads other modules' records and links to them; only manual tasks and alert resolution are acted on there. Tasks are done or cancelled, never deleted.
- Shift reminders and replies (`shift_replies`; rules in `reminders.ts`; `queueShiftReminders` in `rota-service.ts`, run by `tick()` every time; today's team in `src/lib/team-today.ts`). One reminder per person per shift (`reminderKey`, includes the start time), 2 hours before, ignoring quiet hours; the owner's "Send reminders now" sends the rest of today's early. What goes on a phone comes from `waitingFrom`: never staff notes, complaints only as a count. Replies are append-only (latest counts); late and can't-make-it go to managers (`replyMessages`, `replySendAfter`).
- Daily loop (rules in `daily.ts`; inputs gathered by `src/lib/daily-service.ts`; scheduler jobs `queueGasChecks`, `queueReadyAlerts`, `queueDailyDigest` in `rota-service.ts`). A site is only checked on days with published shifts; ready to open also waits until the site has recorded its first checklist (`checklistsStartedOn`, like `trackingFrom`). `sites.ready_by` is the ready-to-open time. `gas_checks` is append-only, one per site per business date (the day the last shift started; the first tap counts). Gas reminders and alerts ignore quiet hours.
- Shift cover (`cover_requests`, `cover_offers`; rules in `cover.ts`; read helpers in `src/lib/cover-service.ts`; page `/manage/cover`). Same site and section, not working or already approved to cover then (any site, the night before and after too), not on approved time off. Where a request stands (`coverState`) is worked out from the row and the shift as it is now, and lists only load shifts that haven't long ended (`shiftEndsAfter`). One request in play per shift (unique index); one live offer per person; offers only while open. Approved becomes "done" once the import shows the coverer on; managers can cancel an approval. The reason is for managers only. The app never writes to the rota sheet. Managers are told as managers, never asked to cover.
